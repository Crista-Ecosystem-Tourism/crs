# Данные для графа маршрутов: куда вносить и что сейчас откуда берётся

Кратко: «умнеет» алгоритм в первую очередь от **качественных точек** (точные координаты и **веса** мест), от **параметров** радиуса/связей/OSRM и — при доработке кода — от **порогов хабов** и формулы оценки рёбер. Ниже — по слоям стека.

---

## 1. Самое важное: вес места (weight)

Вес влияет на всё, что связано с «важностью» узла: кто станет **хабом** (сейчас при весе ≥ 4.0 к точке насильно добавляются лучи к ближайшим соседям), насколько **выгодно** ребро в формуле score, сколько **рёбер** максимум может иметь точка (через `MIN_CONNECTIONS` и `MAX_CONNECTIONS_FACTOR`).

Диапазон в API: **от 0.1 до 10.0** на точку (см. `placesweb_backend/app/api/schemas.py`, модель `PointInput`).

Практика:

- Чем **выше** вес, тем точка **сильнее тянет** сеть: больше связей, чаще попадание в «центр» маршрута, если вес ≥ порога хаба.
- Если все веса одинаковые (например 1.0), геометрия и OSRM решают почти всё; разница только в капе по числу рёбер на узел.

**Где задавать вес сейчас (продуктовый путь):**

- Чат-агрегатор вызывает `placesweb_backend` не напрямую: в **`ai_agent`** в `app/core/services/route.py` вес собирается так: если у места есть **рейтинг** (`place.rating`), он **обрезается** в диапазон 0.1–10 и идёт в поле `weight`; иначе подставляется **`default_weight`** из **`app/config/agent_settings.py`** (сейчас 1.0). То есть **умнее** становится сценарий, когда у мест из RAG/БД **заполнен осмысленный рейтинг** (или вы потом подставите другое поле вместо рейтинга в этом же месте кода).
- **Порог хаба** (4.0) и **число лучей** (6) сейчас **зашиты в коде** в `placesweb_backend/app/core/graph_builder.py` в `_add_hub_spokes` — это не в конфиге. Чтобы «настраивать ум» без правки кода, логичнее вынести их в `Config` (пока такого нет).

**Где задавать вручную / для отладки:**

- Демо-форма **`placesweb_backend/index.html`**: ввод строк вида `lat, lon, weight, name` (см. подсказки на странице).
- Прямой **POST** ` /api/v1/graph/build` (см. раздел 3).

---

## 2. Координаты и порядок точек

- **lat / lon** — широта и долгота; без них точка в агенте **отбрасывается** (см. `_prepare_points` в `route.py`).
- **Порядок** в списке `points` определяет индексы 0, 1, 2, … Сейчас **поиск альтернативных путей** в API идёт от **первой** к **последней** точке в массиве (`source=0`, `target=len-1` в `routes.py`). Учитывайте при сборке маршрута «от А до Б».

**Имя** (`name`) на сам граф **не влияет** — только для отображения и ответа API.

---

## 3. Формат запроса к API графа (основной контракт)

Сервис: **`placesweb_backend`**, эндпоинт **`POST /api/v1/graph/build`**.

Тело (JSON), по смыслу:

- `points`: массив объектов `{ "lat", "lon", "weight", "name" (опц.) }`, от 2 до 500 точек.
- `use_osrm_scoring`: включать ли матрицу OSRM при **оценке** кандидатов в рёбра (по умолчанию в схеме true).
- `base_radius_m`: радиус, внутри которого Delaunay-рёбра и штрафы за длину считаются «нормальными» (по умолчанию 500, в запросе можно 100–5000).
- `min_connections`: минимальное число рёбер у узла при отборе (1–10).
- `k_alternatives`: сколько альтернативных путей от первой к последней точке (0–10).

Полная схема: **`placesweb_backend/app/api/schemas.py`** — `GraphBuildRequest`, `PointInput`.

---

## 4. Серверный конфиг (placesweb) без API-тела

Файл **`placesweb_backend/app/config.py`** — значения по умолчанию, пока запрос их не переопределяет:

- `BASE_RADIUS_M`, `KNN_K`, `MIN_CONNECTIONS`, `MAX_CONNECTIONS_FACTOR`, `ALPHA_WEIGHT_PULL` — плотность сети и сила «притяжения» веса в score.
- `USE_OSRM`, `OSRM_URL`, таймауты, `OSRM_TABLE_BATCH` — **реалистичные** расстояния и **полилинии** по дорогам/тропам (публичный foot-сервер по умолчанию: `https://routing.openstreetmap.de/routed-foot`).
- `K_ALTERNATIVES` — дублирует смысл `k_alternatives` в запросе, если тот не передан; для сценария через агент смотрите `ROUTE_CONFIG` ниже.

Чтобы алгоритм **лучше** следовал реальным маршрутам в вашем регионе, обычно поднимают **свой OSRM** и меняют `OSRM_URL` в этом файле (или выносом в env — если добавите).

---

## 5. Настройки пути «через чат» (ai_agent)

Файл **`ai_agent/app/config/agent_settings.py`**, словарь **`ROUTE_CONFIG`**:

- `url` + `build_endpoint` — куда бить (часто `ROUTE_URL` из env, порт **8003** в docker-compose crs).
- `use_osrm_scoring`, `base_radius_m`, `k_alternatives`, `timeout`, `min_points`, **`default_weight`**.

Логика веса: **`ai_agent/app/core/services/route.py`** — метод `_prepare_points`. Сюда же можно в будущем подставить, например, комбинацию рейтинга и популярности из вашей БД, если сами расширите модель `Place`.

---

## 6. Где «данные сейчас» по цепочке (кратко)

| Что | Где лежит / кто заполняет |
| --- | --- |
| Точки и веса для API | Тело `POST` или демо `placesweb_backend/index.html` |
| Список мест из чата → вес = рейтинг или default | `ai_agent` → `RouteService._prepare_points` |
| Сами места (названия, рейтинг, координаты в RAG) | Ищите пайплайн RAG/vectorization и схему ответа поиска, который склеивает `Place` в агенте (не в `placesweb_backend`) |
| Параметры графа по умолчанию | `placesweb_backend/app/config.py` |
| Параметры вызова графа из агента | `ai_agent/app/config/agent_settings.py` → `ROUTE_CONFIG` |
| Порог хаба и число лучей | **Только в коде** `graph_builder.py`, `_add_hub_spokes` (4.0 и 6) |

---

## 7. Что сделать, если нужно «ещё умнее» без смены модели

1. Улучшать **входные веса** (и источник рейтинга/приоритета в `Place` + `_prepare_points`).
2. Подкрутить **`base_radius_m`**, **`min_connections`**, **`k_alternatives`** (API или `ROUTE_CONFIG`).
3. Стабильный **OSRM** под вашу карту (свой инстанс + `OSRM_URL`).
4. Когда понадобится тонкая настройка **хабов** — вынести `hub_threshold` / `hub_connections` / `ALPHA_WEIGHT_PULL` в конфиг и менять из env или API.
